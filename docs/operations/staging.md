# Staging runbook

**Owner:** Martin · **Last reviewed:** 2026-11-13

Staging runs on Render in Frankfurt ([ADR 0018](../decisions/0018-hosting-on-render-frankfurt.md)),
described by the blueprint
[`infra/render/render.yaml`](../../infra/render/render.yaml). It is for
the team's testing: our own phone numbers (sign-in sends real SMS) and
made-up profiles and trips. Never put customers' data in it.

Requests reach Render through Cloudflare's network, which ends TLS at its
edge ([privacy providers](../compliance/privacy-gdpr.md#providers)).

| Part | Render name | What it is |
| ---- | ----------- | ---------- |
| API and web app | `shareride-staging-api` | Web service built from `apps/api/Dockerfile`; serves `/v1` and the web app on one origin |
| Clean-up | `shareride-staging-clean-up` | Cron job, every hour at minute 17 (UTC): deletes sign-in records past their retention |
| Database | `shareride-staging-db` | PostgreSQL 18 with PostGIS, private network only |
| Settings | `shareride-staging` | Environment group: `NODE_ENV=production`, `APP_ENV=staging`, `LOG_LEVEL` |

The address is the one Render shows for `shareride-staging-api`, usually
`https://shareride-staging-api.onrender.com`. The web app and the API share
it, because `onrender.com` is a public suffix and the refresh cookie must
stay on one site.

## Set it up (once)

Martin's steps. The Vonage account comes first: staging sends real SMS.
Add credit to it: a trial account only sends to the numbers verified on it.

1. Open a Render account with the shared project email address. The free
   Hobby workspace is enough; the services are paid per use (about $15 a
   month, see the [milestone 2 plan](../plans/2026-11-13-milestone-2-hosted-and-connected.md#3-decisions-for-martin)).
   Add a payment card.
2. Connect GitHub and give Render's GitHub app access to the `shareride`
   repository only.
3. Choose **New**, then **Blueprint**, pick the repository and the `main`
   branch, and set **Blueprint Path** to `infra/render/render.yaml`. Render
   reads it and lists the web service, the cron job, the database and the
   environment group.
4. Render asks for the values the blueprint leaves out: `SMS_PROVIDER` is
   `vonage`, and `VONAGE_API_KEY` and `VONAGE_API_SECRET` are the **API
   key** and **API secret** under **API Settings** in the Vonage dashboard.
   They go into Render's secret store only, never into chat, email or the
   repository. `AUTH_SECRET` is generated by Render. If the blueprint was
   applied before these were in it, add the three in the service's
   **Environment** instead: Render only asks when a blueprint is first
   applied.
5. Choose **Apply**. The first build takes a few minutes.
6. Check: the address shows the welcome screen, `/v1/health/ready` answers
   `{"status":"ok"}`, and signing up with your own phone brings a real SMS.
7. Check once that the per-address limit uses the real client address
   ([below](#check-client-addresses)).

### Check client addresses

The API takes the client's address from `X-Forwarded-For`, counting back
two entries (`TRUST_PROXY=2`): Cloudflare appends the client, then Render's
proxy appends the Cloudflare edge. Anything a client sends itself comes
earlier and is ignored. Check it after the first deploy, and again if
Render changes its network:

1. Set `SMS_PAUSED` to `true` (see [Pause SMS](#pause-sms)), so nothing is
   sent. The requests below still count against the limits.
2. From one computer, ask for 11 codes to 11 numbers, each request claiming
   a different address in every header a client could forge:

   ```sh
   STAGING=https://shareride-staging-api.onrender.com
   for i in $(seq 1 11); do
     curl -s -o /dev/null -w '%{http_code}\n' -X POST "$STAGING/v1/auth/phone/start" \
       -H 'Content-Type: application/json' \
       -H "X-Forwarded-For: 198.51.100.$i" -H "True-Client-IP: 198.51.100.$i" \
       -H "CF-Connecting-IP: 198.51.100.$i" \
       -d "{\"phoneNumber\":\"+354690$(printf %04d "$i")\",\"locale\":\"en\"}"
   done
   ```

   Expected: ten `502` (SMS paused), then `429`: the forged addresses did
   not count as different clients. Eleven `502` means a forged header got
   through: stop and fix `TRUST_PROXY` before anyone relies on the limits.
3. From a phone on mobile data (another address), ask for a code in the
   app. It must say the code could not be sent, not that there were too
   many tries. "Too many" means every client shares one address.
4. Set `SMS_PAUSED` back to `false`. The computer from step 2 can ask for
   codes again after an hour.

## Deploy

Every merge to `main` deploys by itself: when the commit's CI checks pass
(`autoDeployTrigger: checksPass`), Render builds the same Dockerfile, runs
`node packages/db/src/migrate-cli.ts --seed-drafts` (migrations, then the
draft legal documents) and starts the new version. Traffic moves to it only
once `/v1/health/ready` answers 200, so a version that cannot reach the
database never takes over. If the migration or the health check fails, the
deploy fails and the running version stays.

Changes to `docs/`, Markdown files and `.claude/` do not deploy.

The clean-up cron job builds and deploys on its own and has no pre-deploy
step, so for a few minutes it can run new code before the web service has
migrated, or old code after. Migrations are expand then contract, and a
failed run is retried the next hour, so this is harmless. It does mean each
merge builds the image twice.

CI already proves the image starts: it builds it and runs
[`infra/docker/smoke-test.sh`](../../infra/docker/smoke-test.sh) against a
test database. To run that locally:

```sh
docker build -f apps/api/Dockerfile -t shareride-api:local .
docker compose -f infra/docker/compose.yml exec db createdb -U shareride shareride_smoke
DATABASE_URL=postgres://shareride:shareride-local-only@localhost:5432/shareride_smoke \
  infra/docker/smoke-test.sh shareride-api:local
```

The script migrates and seeds that database, so never point it at one that
matters. It needs Linux's host networking (`--network host`), as in CI.

To deploy by hand, for example after a failed build: open the service and
choose **Manual Deploy**, then **Deploy latest commit**.

## Roll back

1. Open `shareride-staging-api`, then **Deploys**.
2. Find the last good deploy and choose **Rollback**, then confirm. Render
   reuses that deploy's build, so it is quick.
3. A rollback from the dashboard turns off automatic deploys. Turn them back
   on in **Settings** once the fix is merged.

Migrations are written expand then contract
([conventions](../engineering/conventions.md)), so the previous version
still works with the newer schema and a rollback needs no restore. The cron
job has its own **Deploys** page; roll it back the same way if needed.

## Read logs

Open a service and choose **Logs**. The API writes one JSON line per request
(request ID, route pattern, status, duration; no phone numbers, codes or IP
addresses) plus warnings such as reused refresh tokens, a daily SMS cap
reached in a country, or an `X-Forwarded-For` header without the trusted
proxies' entry (then every client shares one address; see
[Check client addresses](#check-client-addresses)). Search by the
`X-Request-Id` a response carried to follow one request.

The cron job's runs are under its **Events** and **Logs**: each run logs how
many records it deleted, and a failed run exits with an error.

## Error reports and uptime

The API and the clean-up job send unexpected errors to Sentry's EU region
([ADR 0020](../decisions/0020-error-tracking-with-sentry-eu.md)) once
`SENTRY_DSN` is set, and the web app does once `EXPO_PUBLIC_SENTRY_DSN` is
set (it is built in, so it takes effect at the next deploy). The two are
separate Sentry projects. A report from the API carries:

- the error, its stack and the source lines around each frame;
- the release (the commit), the environment, the route pattern and the
  request ID;
- the request's method and path (also the report's transaction name), and
  its `User-Agent`, `Accept-Language` and `Content-Type` headers;
- the Node.js, operating system and machine versions and sizes;
- the API's own recent outgoing requests (method, address and status), such
  as the one to Vonage.

A report from the app carries the error and its stack, the release (the
commit, for the web app), the environment, the browser's or phone's model
and system, and the app's requests to the API just before the error
(method, address, status). From the web app it also carries the screen's
path and the screens visited before it. The web app loads Sentry
separately, so its first screen does not wait for it; an error in its first
second may not be reported.

Never request bodies, cookies, query strings, network addresses, taps or
typing, console output, screenshots, replays, usage sessions or a failed
query's values. Phone numbers,
codes, tokens, email addresses and kennitölur are removed from all text (one
shared rule, `scrubErrorReport` in the domain package). Errors only: a DSN
outside the EU region (`*.ingest.de.sentry.io`) sends nothing, and
`SENTRY_TRACES_SAMPLE_RATE` stops the API from starting, so tracing cannot
be turned on by accident.

Set it up once (Martin):

1. At sentry.io, create the organisation and choose **EU** for data
   storage. It cannot be changed later.
2. Create two projects: `shareride-api` (platform Node.js) and
   `shareride-app` (platform React Native; the name matters, the web build
   uploads to it). In each project's **Settings**, **Security & Privacy**,
   keep the data scrubber and its defaults on, and turn on **Prevent
   Storing of IP Addresses**.
3. Copy each project's DSN (**Settings**, **Client Keys**). They are not
   secrets: they go in the blueprint's `shareride-staging` group, the API's
   as `SENTRY_DSN` (it reaches the API and the clean-up job) and the app's
   as `EXPO_PUBLIC_SENTRY_DSN`.
4. For readable stacks from the web app: in Sentry, **Settings**,
   **Developer Settings**, create an **Organization Token**. In Render, open
   `shareride-staging-api`, **Environment**, **Secret Files**, and add it as
   a file named `sentry-auth-token`. Each build uploads the web app's source
   maps with it and then deletes them, so the site never serves them. If
   the upload fails, the build log says so and the deploy goes on. Then use
   **Manual Deploy**, **Clear build cache & deploy**: a build of a commit
   already built reuses its cached upload step. Render also copies secret
   files into the build's folder; `.dockerignore` keeps this one out of the
   image (a new secret file needs a line there too).
5. Check the API after the next deploy: open the API's **Shell** in Render
   and run `node apps/api/src/sentry-check-cli.ts`. A "Sentry check from
   staging" error should appear in Sentry within a minute, with the commit
   as its release.
6. Check the web app: open the staging address, open the browser's
   developer console and run
   `setTimeout(() => { throw new Error("Web check") })`. After a few seconds
   a "Web check" error should appear in the `shareride-app` project, with
   the commit as its release. Code typed into the console is not the app's,
   so the stack shows Sentry's own source files (under `@sentry/`) rather
   than one long line of minified code: that shows the source maps
   arrived. No release means the build did not get `RENDER_GIT_COMMIT`;
   reports still work.
7. Create an uptime monitor for `<staging address>/v1/health/ready`,
   checked every minute in the `staging` environment, alerting you by email
   and in the Sentry app on your phone.

Sentry keeps reports for 30 days on the free plan, the same as our logs
([retention](../compliance/privacy-gdpr.md)).

## Switch SMS provider

Vonage sends the codes; 46elks is the fallback (ADR 0023), for example if
Vonage stops delivering to one of the Icelandic networks. To switch: open
`shareride-staging-api`, **Environment**, add `ELKS_API_USERNAME` and
`ELKS_API_PASSWORD` (46elks dashboard, Account), set `SMS_PROVIDER` to
`46elks` and save. Render deploys the service again with it. Switch back the
same way. A provider without its keys stops the API from starting, and the
running version stays.

## Pause SMS

If someone abuses sign-in to send SMS (see SMS pumping in
[security](../engineering/security.md)): open `shareride-staging-api`,
**Environment**, add or set `SMS_PAUSED` to `true` and save. Render
deploys the service again with it; sign-in then says the code could not be
sent. Set it back to
`false` (or delete it) when it is safe.

## Restore the database

Staging data is generated, so a restore is rarely needed; we rehearse it
here before the beta. Render keeps point-in-time recovery for 3 days on the
Hobby workspace (7 on Pro).

1. Open `shareride-staging-db`, then **Recovery**, then **Restore
   Database**. Pick a time at least ten minutes ago and a new name.
2. Render creates a new database. Check it with the PSQL command on its
   **Info** page.
3. Point the services at it: in the blueprint, change the name under
   `databases` and the `fromDatabase` name of both services to the new
   database's name, merge, and let the blueprint sync. Changing only the
   services would leave the old name under `databases`, and deleting the old
   database would then make the next sync create an empty one.
4. Once the services work, suspend or delete the old database.

## Rotate a secret

- `AUTH_SECRET`: set a new value in the service's **Environment** (for
  example from `openssl rand -base64 32`). Codes waiting to be used stop
  working and sending limits reset; sessions are not affected.
- Vonage secret: create a second secret in the Vonage dashboard (**API
  Settings**), paste it as `VONAGE_API_SECRET` in the service's
  **Environment**, wait for the deploy, then delete the old secret there.
- 46elks keys: create new ones in the 46elks dashboard, paste them in the
  service's **Environment**, then delete the old ones there.
