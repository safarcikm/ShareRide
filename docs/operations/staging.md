# Staging runbook

**Owner:** Martin · **Last reviewed:** 2026-11-22

Staging runs on Render in Frankfurt ([ADR 0018](../decisions/0018-hosting-on-render-frankfurt.md)),
described by the blueprint
[`infra/render/render.yaml`](../../infra/render/render.yaml). It is for
the team's testing: our own phone numbers (sign-in sends real SMS) and
made-up profiles and trips. Never put customers' data in it.

Requests reach Render through Cloudflare's network, which ends TLS at its
edge ([privacy providers](../compliance/privacy-gdpr.md#providers)).

| Part | Render name | What it is |
| ---- | ----------- | ---------- |
| API and web app | `shareride-staging-api` | Web service built from `apps/api/Dockerfile`; serves `/v1` and the web app on one origin |
| Clean-up | `shareride-staging-clean-up` | Cron job, every hour at minute 17 (UTC): deletes sign-in records past their retention (with the push tokens of sessions ended for being idle), old trip drafts, conversations 12 months after their trip (unless a report covers them: then until 3 years after it closes), makes trips and bookings anonymous 3 years after the trip, the notification log after 90 days, operator console sessions 30 days after they end, passkey challenges and setup links once they expire, and data export files once expired (their dates 30 days later); then erases the accounts whose 7 days after "Delete my account" have ended (spec 11). It takes `AUTH_SECRET` from the API |
| Domains | `staging.puffinride.is`, `staging.skinnar.is` | The web service's own domains: the new one, and the old one until nobody uses it ([Move to puffinride.is](#move-to-puffinrideis)); their DNS records are in ISNIC DNS Hosting ([Point the domain](#point-the-domain)) and Render issues their certificates |
| Database | `shareride-staging-db` | PostgreSQL 18 with PostGIS, private network only |
| Settings | `shareride-staging` | Environment group: `NODE_ENV=production`, `APP_ENV=staging`, `LOG_LEVEL`. `PAYMENT_PROVIDER` is unset, so staging pays with the test provider: no card, no money moves. `WORKER` is unset, so the API runs the notification worker: it pushes through Expo to the phones that registered, with `EXPO_ACCESS_TOKEN` once it is set ([app builds](app-builds.md#android-build-with-push)); `EMAIL_PROVIDER` is unset, so it sends no email and records who would have been emailed, until email is turned on (below) |

Staging's address is **`https://staging.puffinride.is`** (since 2026-11-22,
[ADR 0039](../decisions/0039-rename-to-puffinride.md)); before that it was
`https://staging.skinnar.is`, which still answers until nobody uses it. The
web app and the API share the address, so the refresh cookie stays on one
site, and the operator console is at `/admin` on it. Render's own address for
`shareride-staging-api`, usually `https://shareride-staging-api.onrender.com`,
keeps working too: the domain's DNS record points at it. The web app works
there as well, with a cookie of its own (`onrender.com` is a public suffix),
but the console signs in only on `staging.puffinride.is`.

The domain's DNS is ISNIC DNS Hosting, on ISNIC's own site, where the domain
is registered. ISNIC lists no fee for it beyond the domain's own, and it
holds no personal data.

## Set it up (once)

Martin's steps. The Vonage account comes first: staging sends real SMS.
Add credit to it: a trial account only sends to the numbers verified on it.

1. Open a Render account with the shared project email address. The free
   Hobby workspace is enough; the services are paid per use (about $15 a
   month, see the [milestone 2 plan](../plans/2026-11-13-milestone-2-hosted-and-connected.md#3-decisions-for-martin)).
   Add a payment card.
2. Connect GitHub and give Render's GitHub app access to the `shareride`
   repository only.
3. Choose **New**, then **Blueprint**, pick the repository and the `main`
   branch, and set **Blueprint Path** to `infra/render/render.yaml`. Render
   reads it and lists the web service, the cron job, the database and the
   environment group.
4. Render asks for the values the blueprint leaves out: `SMS_PROVIDER` is
   `vonage`, and `VONAGE_API_KEY` and `VONAGE_API_SECRET` are the **API
   key** and **API secret** under **API Settings** in the Vonage dashboard.
   They go into Render's secret store only, never into chat, email or the
   repository. `AUTH_SECRET` is generated by Render. If the blueprint was
   applied before these were in it, open the service's **Environment**
   instead: set `SMS_PROVIDER` to `vonage` and add `VONAGE_API_KEY` and
   `VONAGE_API_SECRET`. Render only asks when a blueprint is first applied.
5. Choose **Apply**. The first build takes a few minutes.
6. Point the domain at staging ([below](#point-the-domain)).
7. Check: `https://staging.puffinride.is` shows the welcome screen,
   `https://staging.puffinride.is/v1/health/ready` answers `{"status":"ok"}`,
   and signing up with your own phone brings a real SMS.
8. Check once that the per-address limit uses the real client address
   ([below](#check-client-addresses)).

### Point the domain

These steps set up `staging.skinnar.is` in 2026-11; `staging.puffinride.is`
took the same record ([Move to puffinride.is](#move-to-puffinrideis), step 4).
Once, after the blueprint is applied. ISNIC's steps work on a phone;
Render's dashboard is easier on a computer.

1. At [isnic.is](https://www.isnic.is), log in and open **My page**, then
   the domain `skinnar.is`. Under **Nameservers**, choose **Redelegate**,
   pick **ISNIC DNS Hosting** and **Submit**. Within about 10 minutes the
   domain's page lets you add DNS records. (Skip this if the domain already
   has a DNS host and add the record there instead. On Cloudflare, set the
   record to **DNS only**: a proxy of our own would add a third entry to
   `X-Forwarded-For`, see [below](#check-client-addresses).)
2. In Render, open `shareride-staging-api`. Its own address is at the top
   of the page, such as `shareride-staging-api.onrender.com` (Render adds a
   few letters when the name was taken). Under **Settings**, **Custom
   Domains**, `staging.skinnar.is` is listed from the blueprint.
3. At ISNIC, add a record: type **CNAME**, name `staging`, and as its value
   the service's own address from step 2, without `https://`. Add no
   `AAAA` record: Render answers on IPv4 only.
4. In Render, choose **Verify** next to `staging.skinnar.is`. If it fails,
   wait a few minutes and try again. Once the certificate shows as issued,
   `https://staging.skinnar.is` answers; Render renews the certificate by
   itself.

### Check client addresses

The API takes the client's address from `X-Forwarded-For`, counting back
two entries (`TRUST_PROXY=2`): Cloudflare appends the client, then Render's
proxy appends the Cloudflare edge. Anything a client sends itself comes
earlier and is ignored. Render serves `staging.skinnar.is` through the same
network, so this holds for both addresses as long as nothing of ours sits in
front (the DNS record is a plain CNAME). Check it after the first deploy,
and again if Render changes its network or the domain's DNS:

1. Set `SMS_PAUSED` to `true` (see [Pause SMS](#pause-sms)), so nothing is
   sent. The requests below still count against the limits.
2. From one computer, ask for 11 codes to 11 numbers, each request claiming
   a different address in every header a client could forge:

   ```sh
   STAGING=https://staging.puffinride.is
   for i in $(seq 1 11); do
     curl -s -o /dev/null -w '%{http_code}\n' -X POST "$STAGING/v1/auth/phone/start" \
       -H 'Content-Type: application/json' \
       -H "X-Forwarded-For: 198.51.100.$i" -H "True-Client-IP: 198.51.100.$i" \
       -H "CF-Connecting-IP: 198.51.100.$i" \
       -d "{\"phoneNumber\":\"+354690$(printf %04d "$i")\",\"locale\":\"en\"}"
   done
   ```

   Expected: ten `502` (SMS paused), then `429`: the forged addresses did
   not count as different clients. Eleven `502` means a forged header got
   through: stop and fix `TRUST_PROXY` before anyone relies on the limits.
3. From a phone on mobile data (another address), ask for a code in the
   app. It must say the code could not be sent, not that there were too
   many tries. "Too many" means every client shares one address.
4. Set `SMS_PAUSED` back to `false`. The computer from step 2 can ask for
   codes again after an hour.

## Move to puffinride.is

Staging moves from `staging.skinnar.is` to `staging.puffinride.is`, as
ShareRide becomes PuffinRide ([ADR 0039](../decisions/0039-rename-to-puffinride.md)).
The blueprint lists both addresses, so both answer until step 6 switches the
settings, and nothing stops working in between. Martin's steps, in order:

1. **DNS hosting.** At [isnic.is](https://www.isnic.is), **My page**, the
   domain `puffinride.is`, **Nameservers**, **Redelegate**, **ISNIC DNS
   Hosting**, **Submit**. Within about 10 minutes the domain's page lets you
   add records.
2. **The mailbox `admin@puffinride.is`,** for the operator's own accounts
   (Google, Apple, Render, Mailjet, Sentry), never for members' mail. It is a
   Google Workspace mailbox (Business Starter, paid per user and month, the
   first 14 days free). At [workspace.google.com](https://workspace.google.com),
   **Get started**: you already have a domain, `puffinride.is`; create the
   user `admin`. Google then shows three records to add in ISNIC:
   - the proof that the domain is yours: type **TXT**, name empty, value
     `google-site-verification=…` (copy it), then **Verify** in Google;
   - mail delivery: type **MX**, name empty, priority `1`, value
     `smtp.google.com` (the only MX record);
   - DKIM: in the Admin console, **Apps**, **Google Workspace**, **Gmail**,
     **Authenticate email**, **Generate new record**; add it as type
     **TXT**, name `google._domainkey`, and choose **Start authentication**
     once ISNIC has it. Google may wait a day or two after sign-up before it
     offers the key.

   Leave out Google's SPF record: step 5 makes one for Google and Mailjet
   together. Turn on two-step sign-in: in the Admin console, **Security**,
   **Authentication**, **2-Step Verification**, allow it, then turn it on
   for `admin@` at [myaccount.google.com](https://myaccount.google.com) with
   a passkey or an authenticator app, and keep its backup codes in your
   password manager, not in a file or chat. Check: an email from your own
   address to `admin@puffinride.is` arrives. Add no `hello@` address: a
   member's reply to our emails would then be member data in this mailbox
   (ADR 0039); Google returns such replies to their sender.
3. **`puffinride.com`, at Cloudflare,** leads to `puffinride.is`. In
   Cloudflare, the domain `puffinride.com`, **DNS**, **Records**: type
   **A**, name `@`, IPv4 `192.0.2.1`, **Proxied**; and the same with name
   `www`. The address goes nowhere; it only lets Cloudflare answer for the
   domain. Then **Rules**, **Redirect Rules**, **Create rule**: **Wildcard
   pattern**, request URL `http*://*puffinride.com/*`, target URL
   `https://puffinride.is/`, status `301`. Nothing is needed in Render:
   Cloudflare answers for `.com` itself, and Render never sees it.
   `puffinride.is` itself gets a website with production, so until then
   the redirect leads to an address that does not answer yet. As
   `puffinride.com` sends no email, add type **TXT**, name `@`, value
   `v=spf1 -all`, and type **TXT**, name `_dmarc`, value
   `v=DMARC1; p=reject`, so nobody can send email in its name. (It can
   become an alias domain in Google Workspace later, if mail to
   `@puffinride.com` should arrive; it then needs Google's records too.)
4. **Staging's new address.** In ISNIC, add type **CNAME**, name `staging`,
   and as its value the same `onrender.com` address as the `staging` record
   of `skinnar.is` (it is at the top of `shareride-staging-api`'s page in
   Render). No `AAAA` record. In Render, `shareride-staging-api`,
   **Settings**, **Custom Domains**, choose **Verify** next to
   `staging.puffinride.is`. Check:
   `https://staging.puffinride.is/v1/health/ready` answers
   `{"status":"ok"}`.
5. **Email from puffinride.is.** In Mailjet, **Account settings**,
   **Domains and senders**, add `puffinride.is` and add the TXT records it
   shows for ownership and DKIM, as in [Turn on email](#turn-on-email). Then
   one SPF record for both senders, Google Workspace and Mailjet: type
   **TXT**, name empty, value
   `v=spf1 include:_spf.google.com include:spf.mailjet.com ~all`. Two SPF
   records on one domain break both. And DMARC: type **TXT**, name
   `_dmarc`, value `v=DMARC1; p=none`. Wait until Mailjet shows the domain
   as validated, with SPF and DKIM in order.
6. **Tell Claude.** Claude switches the blueprint's `ADMIN_ORIGIN`,
   `WEB_APP_URL` and `API_ORIGIN` to `https://staging.puffinride.is`,
   `EMAIL_FROM` to `hello@puffinride.is`, and the app builds' API address.
7. **After that deploy, the console.** Its passkeys belong to the old
   address. In the API's **Shell** in Render, run
   `node apps/api/src/operator-cli.ts add <your phone number>`, open the
   link and save a new passkey ([Sign in to the console](#sign-in-to-the-console)).
   Sign in at `https://staging.puffinride.is/admin` from then on, and delete
   the old passkey from your password manager. Testers sign in again on the
   new address.
8. **Google sign-in:** follow [Turn on Google sign-in](#turn-on-google-sign-in),
   which uses the new names and address, signed in to Google Cloud as
   `admin@puffinride.is`.
9. **Sign in with Apple:** follow
   [Turn on Sign in with Apple](#turn-on-sign-in-with-apple), with the
   `is.puffinride.…` IDs, including `hello@puffinride.is` for Apple's email
   relay. A Services ID cannot be renamed: one made earlier with an old name
   stays unused.
10. **Sentry:** change the uptime monitor's address to
   `https://staging.puffinride.is/v1/health/ready`. The organisation's name
   may become PuffinRide; keep its short name (slug) as it is.
11. **The old address,** once nobody uses it: tell Claude, who removes
    `staging.skinnar.is` from the blueprint. Then delete the `staging`
    record of `skinnar.is` in ISNIC, and, if any were made earlier, the
    domain `skinnar.is` in Mailjet, a redirect URI on `staging.skinnar.is`
    in Google Cloud and `hello@skinnar.is` in Apple's email relay.

## Sign in to the console

The operator console signs in with passkeys only, bound to one address
([ADR 0028](../decisions/0028-operator-console-web-app-and-passkeys.md)):
the blueprint sets `ADMIN_ORIGIN` to `https://staging.puffinride.is`, so the
domain must answer first ([Move to puffinride.is](#move-to-puffinrideis),
step 4). Once:

1. Sign up in the app with your own phone, if you have not yet. While the
   beta is closed a new account needs an invite code: open the API's
   **Shell** in Render and run
   `node apps/api/src/invite-cli.ts add "First testers" 20`, which prints
   a group code for 20 accounts that works for 30 days (a third number
   sets the days). Later codes are made in the console.
2. Open the API's **Shell** in Render and run
   `node apps/api/src/operator-cli.ts add <your phone number>`. It gives
   your account the operator role and prints a link that works once, for
   30 minutes.
3. Open the link on the laptop or phone you will use, and save a passkey
   there (Touch ID, Face ID, Windows Hello or a security key). Add your
   other devices from inside the console.
4. From then on, sign in at `https://staging.puffinride.is/admin`.

### Sign in with a password for now

While passkeys are being fixed, the console also takes your phone number and
a password set in Render
([ADR 0041](../decisions/0041-console-password-for-now.md)):

1. Make a password of 12 characters or more that you use nowhere else, for
   example four random words, and keep it in your password manager.
2. In Render, open **shareride-staging-api**, then **Environment**, and
   **Add Environment Variable**: key `ADMIN_PASSWORD`, value your password.
   **Save Changes** (Render redeploys the API, a few minutes).
3. Open `https://staging.puffinride.is/admin`. Under **Or sign in with a
   password**, type your phone number and the password, then **Sign in with
   the password**.
4. On the **Passkeys** page, save a passkey for this device right away (it
   works for 5 minutes after signing in).

To turn it off, delete `ADMIN_PASSWORD` in the same place. Then check the
**Passkeys** page for passkeys you did not save, and the audit log
(`operator.`) for sign-ins with method `password` and passkeys added or
removed after them: a password sign-in can change passkeys for 5 minutes.
The API refuses to start with `ADMIN_PASSWORD` on production.

### Lost every passkey

Run step 2 of the first list above again for a new link. To take the role
away: `node apps/api/src/operator-cli.ts remove <phone number or user
ID>`, which also ends that account's console sessions and deletes its
passkeys; `list` shows the operators. Changing `ADMIN_ORIGIN` (for example
when the console moves to a host name of its own, milestone 12) means
saving passkeys again with a new link.

## Deploy

Every merge to `main` deploys by itself: when the commit's CI checks pass
(`autoDeployTrigger: checksPass`), Render builds the same Dockerfile, runs
`node packages/db/src/migrate-cli.ts --seed-drafts` (migrations, then the
draft legal documents, the sample meeting points with their distances, and
the sample trips, replaced with fresh dates on each deploy)
and starts the new version. Traffic moves to it only
once `/v1/health/ready` answers 200, so a version that cannot reach the
database never takes over. If the migration or the health check fails, the
deploy fails and the running version stays.

Changes to `docs/`, Markdown files and `.claude/` do not deploy.

The clean-up cron job builds and deploys on its own and has no pre-deploy
step, so for a few minutes it can run new code before the web service has
migrated, or old code after. Migrations are expand then contract, and a
failed run is retried the next hour, so this is harmless. It does mean each
merge builds the image twice.

CI already proves the image starts: it builds it and runs
[`infra/docker/smoke-test.sh`](../../infra/docker/smoke-test.sh) against a
test database. To run that locally:

```sh
docker build -f apps/api/Dockerfile -t shareride-api:local .
docker compose -f infra/docker/compose.yml exec db createdb -U shareride shareride_smoke
DATABASE_URL=postgres://shareride:shareride-local-only@localhost:5432/shareride_smoke \
  infra/docker/smoke-test.sh shareride-api:local
```

The script migrates and seeds that database, so never point it at one that
matters. It needs Linux's host networking (`--network host`), as in CI.

A build that passes in CI can still fail on Render. Metro starts a bundling
worker per CPU it sees, each a few hundred MB, and Render's build machines
can show it more CPUs than CI's. A build log that stops with no error during
the web export (`expo export`) most likely ran out of memory (2026-11-22):
the Dockerfile caps Metro at two workers, about 1.4 GB, so keep that cap
when changing the export.

To deploy by hand, for example after a failed build: open the service and
choose **Manual Deploy**, then **Deploy latest commit**.

## Roll back

1. Open `shareride-staging-api`, then **Deploys**.
2. Find the last good deploy and choose **Rollback**, then confirm. Render
   reuses that deploy's build, so it is quick.
3. A rollback from the dashboard turns off automatic deploys. Turn them back
   on in **Settings** once the fix is merged.

Migrations are written expand then contract
([conventions](../engineering/conventions.md)), so the previous version
still works with the newer schema and a rollback needs no restore. The cron
job has its own **Deploys** page; roll it back the same way if needed.

Data a newer version wrote can still trip an older one. Once a driver has
removed a stop from a trip (milestone 6, PR 6b), a version from before
that shows the stop again, books on the wrong stops of that trip and
cannot read its conversations' "Stop removed" line. Past that point, roll
forward with a fix rather than back. From the closed beta on, such changes
ship in two deploys ([conventions](../engineering/conventions.md#database)),
so a rollback stays safe.

## Read logs

Open a service and choose **Logs**. The API writes one JSON line per request
(request ID, route pattern, status, duration; no phone numbers, codes or IP
addresses) plus warnings such as reused refresh tokens, a daily SMS cap
reached in a country, or an `X-Forwarded-For` header without the trusted
proxies' entry (then every client shares one address; see
[Check client addresses](#check-client-addresses)). Search by the
`X-Request-Id` a response carried to follow one request.

The cron job's runs are under its **Events** and **Logs**: each run logs how
many records it deleted, and a failed run exits with an error.

## Error reports and uptime

The API and the clean-up job send unexpected errors to Sentry's EU region
([ADR 0020](../decisions/0020-error-tracking-with-sentry-eu.md)) once
`SENTRY_DSN` is set, and the web app does once `EXPO_PUBLIC_SENTRY_DSN` is
set (it is built in, so it takes effect at the next deploy). The two are
separate Sentry projects. A report from the API carries:

- the error, its stack and the source lines around each frame;
- the release (the commit), the environment, the route pattern and the
  request ID;
- the request's method and path (also the report's transaction name), and
  its `User-Agent`, `Accept-Language` and `Content-Type` headers;
- the Node.js, operating system and machine versions and sizes;
- the API's own recent outgoing requests (method, address and status), such
  as the one to Vonage.

A report from the app carries the error and its stack, the release (the
commit, for the web app), the environment, the browser's or phone's model
and system, and the app's requests to the API just before the error
(method, address, status). From the web app it also carries the screen's
path and the screens visited before it. The web app loads Sentry
separately, so its first screen does not wait for it; an error in its first
second may not be reported.

Never request bodies, cookies, query strings, network addresses, taps or
typing, console output, screenshots, replays, usage sessions or a failed
query's values. Phone numbers,
codes, tokens, email addresses and kennitölur are removed from all text (one
shared rule, `scrubErrorReport` in the domain package). Errors only: a DSN
outside the EU region (`*.ingest.de.sentry.io`) sends nothing, and
`SENTRY_TRACES_SAMPLE_RATE` stops the API from starting, so tracing cannot
be turned on by accident.

Set it up once (Martin). Steps 1 to 3 were done on 2026-11-19: the
organisation is `shareride-ehf` in the EU region (`de.sentry.io`), both
projects scrub with the defaults and store no IP addresses, and their DSNs
are in the blueprint.

1. At sentry.io, create the organisation and choose **EU** for data
   storage. It cannot be changed later.
2. Create two projects: `shareride-api` (platform Node.js) and
   `shareride-app` (platform React Native; the name matters, the web build
   uploads to it). In each project's **Settings**, **Security & Privacy**,
   keep the data scrubber and its defaults on, and turn on **Prevent
   Storing of IP Addresses**. In the organisation's own **Security &
   Privacy**, turn on the same three, so a later project cannot miss them,
   and turn off **Allow Shared Issues**, so no issue gets a public link.
3. Copy each project's DSN (**Settings**, **Client Keys**). They are not
   secrets: they go in the blueprint's `shareride-staging` group, the API's
   as `SENTRY_DSN` (it reaches the API and the clean-up job) and the app's
   as `EXPO_PUBLIC_SENTRY_DSN`.
4. For readable stacks from the web app: in Sentry, **Settings**,
   **Developer Settings**, create an **Organization Token**. In Render, open
   `shareride-staging-api`, **Environment**, **Secret Files**, and add it as
   a file named `sentry-auth-token`. Each build uploads the web app's source
   maps with it and then deletes them, so the site never serves them. If
   the upload fails, the build log says so and the deploy goes on. Then use
   **Manual Deploy**, **Clear build cache & deploy**: a build of a commit
   already built reuses its cached upload step. Render also copies secret
   files into the build's folder; `.dockerignore` keeps this one out of the
   image (a new secret file needs a line there too).
5. Check the API after the next deploy: open the API's **Shell** in Render
   and run `node apps/api/src/sentry-check-cli.ts`. A "Sentry check from
   staging" error should appear in Sentry within a minute, with the commit
   as its release.
6. Check the web app: open the staging address, open the browser's
   developer console and run
   `setTimeout(() => { throw new Error("Web check") })`. After a few seconds
   a "Web check" error should appear in the `shareride-app` project, with
   the commit as its release. Code typed into the console is not the app's,
   so the stack shows Sentry's own source files (under `@sentry/`) rather
   than one long line of minified code: that shows the source maps
   arrived. No release means the build did not get `RENDER_GIT_COMMIT`;
   reports still work.
7. Create an uptime monitor for `<staging address>/v1/health/ready`,
   checked every minute in the `staging` environment, alerting you by email
   and in the Sentry app on your phone.

Sentry keeps reports for 30 days on the free plan, the same as our logs
([retention](../compliance/privacy-gdpr.md)).

## Switch SMS provider

Vonage sends the codes; 46elks is the fallback (ADR 0023), for example if
Vonage stops delivering to one of the Icelandic networks. To switch: open
`shareride-staging-api`, **Environment**, add `ELKS_API_USERNAME` and
`ELKS_API_PASSWORD` (46elks dashboard, Account), set `SMS_PROVIDER` to
`46elks` and save. Render deploys the service again with it. Switch back the
same way. A provider without its keys stops the API from starting, and the
running version stays.

## Pause SMS

If someone abuses sign-in to send SMS (see SMS pumping in
[security](../engineering/security.md)): open `shareride-staging-api`,
**Environment**, add or set `SMS_PAUSED` to `true` and save. Render
deploys the service again with it; sign-in then says the code could not be
sent. Set it back to
`false` (or delete it) when it is safe.

## Turn on email

Staging sends no email until Mailjet sends for `puffinride.is` (ADR 0027).
The blueprint already sets the sender, `EMAIL_FROM` = `hello@puffinride.is`,
and `WEB_APP_URL` = `https://staging.puffinride.is`, where the emails' links
lead. Martin's steps; if [Move to puffinride.is](#move-to-puffinrideis)
step 5 is done, the domain is in Mailjet already, with its one SPF and one
DMARC record: start at step 2.

1. In Mailjet, **Account settings**, **Domains and senders**: add the

   **Statistics** list it, and show no opens or clicks, as tracking is off.

## Restore the database

Staging data is generated, so a restore is rarely needed; we rehearse it
here before the beta. Render keeps point-in-time recovery for 3 days on the
Hobby workspace (7 on Pro).

1. Open `shareride-staging-db`, then **Recovery**, then **Restore
   Database**. Pick a time at least ten minutes ago and a new name.
2. Render creates a new database. Check it with the PSQL command on its
   **Info** page.
3. Bring over the deletions since the restore's point, so the restored
   database never serves an erased account and never erases one kept
   (spec 11, 3.7). Copy the new database's **Internal Database URL** from
   its **Info** page, open the API's **Shell** (it still uses the old
   database) and run:

   ```sh
   PREVIOUS_DATABASE_URL="$DATABASE_URL" DATABASE_URL="<new database URL>" \
     node apps/api/src/privacy-cli.ts reapply-erasures
   ```

   It takes each "Delete my account" or "Keep my account" pressed in the
   old database since, then erases again every erased account that came
   back, and says how many of each. If it ends with `Failed:`, do not go
   on: the log names each account, and the step can be run again once
   fixed. If the old database is lost, leave out `PREVIOUS_DATABASE_URL`:
   deletions asked for, undone or finished after the restore's point are
   then missed, a gap point-in-time recovery keeps to minutes.
4. Point the services at it: in the blueprint, change the name under
   `databases` and the `fromDatabase` name of both services to the new
   database's name, merge, and let the blueprint sync. Changing only the
   services would leave the old name under `databases`, and deleting the old
   database would then make the next sync create an empty one.
5. Run step 3 again from the API's Shell, now with
   `PREVIOUS_DATABASE_URL="<old database URL>"` and the shell's own
   `DATABASE_URL`, for what happened in the old database in the meantime.
   A change made in the new database since is newer, so it stays.
6. Once the services work, suspend or delete the old database.

## Retention runs and holds

The hourly clean-up records each retention rule's run (spec 11, 3.7). To
see the last run of each, open the API's **Shell** and run:

```sh
node apps/api/src/privacy-cli.ts runs
```

A rule whose last run is over an hour old, or `never run`, has failed:
Sentry has the error, tagged with the rule.

To keep a person's, trip's or booking's records past their date for a
dispute, chargeback or legal claim, give the ID, the last day to keep them
(Iceland time), a reason that names the case rather than the person, and
your own user ID or phone number for the audit log:

```sh
node apps/api/src/privacy-cli.ts hold booking <booking ID> \
  --until 2027-03-31 --reason "Chargeback 4411" --by <your user ID>
node apps/api/src/privacy-cli.ts holds
node apps/api/src/privacy-cli.ts end-hold <hold ID> --by <your user ID>
```

`holds` lists those in force, nearest end first. Once a hold ends, its
records go at the next clean-up if their own dates have passed.

## Answer privacy requests

What people send through "Ask about my data" must be answered within a
month (R11.7). To list those waiting, nearest due first, with their text:

```sh
node apps/api/src/privacy-cli.ts requests
```

A request past its due date ends with `overdue`. To answer one, give your
own user ID or phone number for the audit log:

```sh
node apps/api/src/privacy-cli.ts answer <request ID> \
  --text "<the answer>" --by <your user ID>
```

The answer goes to the person by email within a minute, in their
language, with the day they asked. Write it as you would an email: it is
sent as written, and stays with the request for 3 years. A request can be
answered once. If the account has been deleted since, the answer is kept
but no email goes.

## Rotate a secret

- `AUTH_SECRET`: set a new value in the service's **Environment** (for
  example from `openssl rand -base64 32`). Codes waiting to be used stop
  working and sending limits reset; sessions are not affected. Data
  exports waiting to be downloaded can no longer be read (people ask for
  a new one), and the numbers of erased suspended accounts are no longer
  recognised, so they could sign up again. The clean-up job takes the
  new value from the API at its next deploy.
- Vonage secret: an account holds two secrets at most, so first revoke the
  one not in use if there are two. Create a new secret in the Vonage
  dashboard (**Settings**, **API
  Settings**), paste it as `VONAGE_API_SECRET` in the service's
  **Environment**, wait for the deploy, then revoke the old secret there.
- 46elks keys: create new ones in the 46elks dashboard, paste them in the
  service's **Environment**, then delete the old ones there.
- Photo bucket keys: generate new S3 credentials in the Hetzner project,
  paste them as `PHOTO_BUCKET_ACCESS_KEY` and `PHOTO_BUCKET_SECRET_KEY` in
  the service's **Environment**, wait for the deploy, then delete the old
  ones there.
